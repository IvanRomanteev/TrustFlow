# TrustFlow M1 — Real Meta Intelligence

## Fake / live switch (the only switch)

| Setting | Value | Behaviour |
|---|---|---|
| `TRUSTFLOW_LLM_MODE` | `fake` (default) | Deterministic `FakeLLMProvider`. Offline, zero cost. Tests and demo. |
| `TRUSTFLOW_LLM_MODE` | `live` | `MetaResponsesProvider` against the Meta Responses API. Requires `MODEL_API_KEY`. Any live failure raises and the workflow fails closed. **Never** falls back to Fake. |

Keys: TrustFlow reads `MODEL_API_KEY` (fallback: legacy `TRUSTFLOW_LLM_API_KEY`).
Muse's `META_API_KEY` is not read implicitly. Keys are never logged,
persisted, or included in reports; `/health` exposes only mode and model names.

Models: planning + independent semantic review use `muse-wonder-1.0`
(`TRUSTFLOW_PLANNING_MODEL`, `TRUSTFLOW_REVIEW_MODEL`); `muse-spark-1.3`
(`TRUSTFLOW_FAST_MODEL`) is available for lower-cost inference. Base URL
default `https://api.meta.ai/v1`, endpoint `/responses`, structured output via
`text.format` with flat, non-recursive schemas (recursive schemas return
HTTP 400 per official docs). Parameters verified at
https://dev.meta.ai/docs/structured-output and
https://dev.meta.ai/docs/pricing-rate-limits.

## Round-7 remediation (round-6 re-review of 98d3aaa, N1 only)

Status: **N1 fixed by the developer, awaiting independent
confirmation — M1 is not accepted.** The 98d3aaa re-review independently
marked **R1/F1 and R2/F2 VERIFIED FIXED** and kept the R3 strict-type
gate open only via this new regression; F3/F5 remain verified fixed.

- **N1 (overflow in `strict_json_number`):** `float(value)` on a huge
  JSON integer (semantic `confidence=±10**400` after a committed
  transfer) raised `OverflowError` outside the typed validation path,
  producing HTTP 500 and an unrecoverable `VERIFYING`. The validator
  in `src/trustflow/tools/ledger.py` is now total for JSON int/float:
  an overflowing conversion becomes `ValueError`, so Pydantic raises
  `ValidationError`, the reviewer raises `LLMResponseError`, and the
  engine follows the existing bounded verification-only recovery
  (`VERIFICATION_PENDING`, then `FAILED` at the attempt limit) with
  usage and sanitized `semantic_review_failed` audit preserved. No
  general exception catch was added to the engine; bool/string and
  non-finite inputs are still rejected, the confidence range is
  unchanged, and no value is clamped into range. Because the validator
  is shared, `±10**400` in transfer/FX `amount` is likewise rejected
  by controlled validation before any side effect. Regression tests:
  `tests/unit/test_m1_n1.py` (6 failed / 3 passed on 98d3aaa, 9 passed
  after the fix), covering healthy `verify-retry` to `COMPLETED` with
  exactly one transfer, bounded exhaustion, per-attempt usage
  (input 7 / output 11, no duplicates), audit history surviving the
  cleared active error, and the public GET/audit/verify-retry/reconcile
  endpoints in their defined states.

## Round-6 remediation (re-review of 71df99c, residual R1–R3)

Status: **R1–R3 fixed by the developer, awaiting independent
confirmation — M1 is not accepted.** The 71df99c re-review independently
marked **F3 and F5 VERIFIED FIXED**; F1/F2/F4 stayed open only via the
residual findings below. Regression tests in
`tests/unit/test_m1_round6.py` (28 tests): 15 failed / 13 passed on
71df99c, all green after the fix.

- **R1 (extreme usage):** provider ingestion accepts a token count only
  in `0..MAX_TOKEN_COUNT` (10^9). An out-of-range or otherwise invalid
  count is recorded as unknown (`null`) for that field only — never
  replaced by an invented number — while a valid sibling count (e.g.
  `output_tokens=11`) is preserved. Contract correction: an ordinary
  invalid count yields unknown usage, **not** an `LLMResponseError`, and
  does not hide invalid semantic output (missing fields still fail
  validation). `estimate_cost` is computed in `Decimal` and returns
  infinity beyond float range instead of raising `OverflowError`. In
  `UsageTracker.record` the cost is computed per item immediately
  before that item is appended; safety for external counts rests on
  the ingestion bound plus this non-raising arithmetic, so an attempt
  record is never lost to cost arithmetic. The post-transfer
  extreme-usage payload now completes through the normal path with the
  semantic record saved; public `verify-retry` answers in a defined
  state and there is exactly one transfer.
- **R2 (budget inside the retry loop):** `Planner` and
  `SemanticReviewer` pass their per-workflow `UsageTracker` and the
  reservation estimate explicitly per call to tracker-aware providers
  (`supports_attempt_tracker`); the provider holds no shared
  current-workflow state, so concurrent workflows stay isolated. Each
  interim attempt (retryable HTTP error, transport timeout) is recorded
  in the originating workflow's tracker immediately, and the next HTTP
  request is allowed only after a fresh `reserve()` against the
  now-known totals (budget 1500 / reservation 1457 blocks a retry after
  both 2000-token and 100-token first attempts). Terminal attempts are
  recorded by the provider and raised without a record so callers never
  double-count; a successful final record is returned for the caller to
  record once, pre-labelled with the shared logical `attempt`
  (`transport_attempt` keeps counting HTTP tries). Incurred usage is
  preserved when a budget check rejects a retry. **Unknown-usage
  policy:** unknown attempts consume no known tokens; the re-reservation
  re-checks the full per-call estimate against known totals. Actual
  provider billing for unknown attempts is not bounded by this
  application-side enforcement, which remains an estimate, not a
  provider billing guarantee.
- **R3 (strict JSON types):** external numeric fields no longer accept
  Python coercion. `limit`, transfer/FX `amount` and semantic
  `confidence` reject booleans (an `int` subclass) and numeric strings
  (`limit=true/"1"/"100"`, `confidence=true/"0.8"` all fail). Valid
  values are unchanged: confidence 0/1/0.8, limit 1/100. Integer-valued
  JSON numbers (`limit=1.0`) are accepted as integers, matching JSON
  Schema `integer`; fractional values (1.5) are rejected.

The re-review's diagnostic probe that asserted the `OverflowError`
itself (`test_confirm_extreme_usage_exception_origin`) is preserved
unchanged in the review catalogue; by design it now fails in its
original form because the defect is gone — absence of the defect is
proven by the round-6 tests instead. Adapted independent probes: 38/38
pass on the fixed source; extra deep/accounting probes: 45 passed with
only that diagnostic failing. Original probes unchanged: 36 passed /
2 failed (the two probe-side failures already adjudicated in the
re-review).

## Round-5 remediation (independent offline audit of 89c1812, F1–F5)

Status: **fixed by the developer, awaiting independent re-review — M1 is
not accepted.** Baseline audited: `89c18120e4555949ca96c11b12bd5eaeeac9ff05`
(BLOCKED, F1–F5 open). Regression tests in
`tests/unit/test_m1_round5.py` (21 tests) failed on the baseline
(19 failed, 2 passed) before the fix.

- **F1 (malformed envelope):** `MetaResponsesProvider` validates the
  envelope, `output`/`content` structure and usage values before reading
  any field. Non-object bodies, non-list output, invalid token values and
  unparseable JSON become `LLMResponseError` with a sanitized reason and
  the incurred usage record (invalid/absent tokens stay `null`/unknown,
  never fabricated). After a committed transfer this lands in the bounded
  verification-only recovery (`VERIFICATION_PENDING`, or `FAILED` at the
  semantic attempt limit): no `VERIFYING` deadlock, no payment re-execution,
  and arbitrary programming errors are not caught by these handlers.
- **F2 (per-attempt accounting):** every HTTP attempt (retryable 429/5xx,
  transport timeout, terminal failure) produces an `LLMCallRecord` before
  retry/raise, with available tokens/request ID preserved. `attempt` is
  the logical-call attempt assigned by the tracker; `transport_attempt`
  is the HTTP attempt within it. The final record carries earlier ones as
  `prior_attempts`; `UsageTracker.record` expands them into flat records
  sharing the logical attempt, so successful responses are never
  double-counted and retry tokens count toward the workflow budget. This
  remains an application-side estimate, **not** a provider billing cap.
- **F3 (revision bounds):** `PolicyEngine.check_bounds` runs for every
  revised plan before intent assignment/authorization and before any step
  of the revision executes; an oversized revision fails the run. A new
  approval never lifts `max_steps`.
- **F4 (schema parity):** `SemanticReviewInput` now requires `issues` and
  `summary` exactly as `REVIEW_SCHEMA` does (no local defaults); an
  incomplete semantic PASS is malformed and cannot complete a workflow.
  `PLAN_SCHEMA` expresses `list_transactions.limit` as integer 1–100, the
  same bounds as local `ListTransactionsArgs`, and the planning prompt
  states them. **Documented flat-schema limitation:** the single flat step
  schema cannot express per-tool constraints (e.g. `amount > 0` only for
  transfers, known-account enums), because the same fields are emitted as
  placeholders for other tools; strict local Pydantic validation in
  `validate_steps` remains authoritative for those. Full parity is
  claimed only for the constraints the flat schema can express, proven
  by the round-5 tests (missing fields, wrong types, limit 0/1/100/101).
- **F5 (outage history):** the semantic exception branch writes a
  sanitized `semantic_review_failed` audit event (error, attempt number,
  recovery state) before returning. Successful `verify-retry` still
  clears the active `error`, but the outage event remains in the audit.

Independent probes preserved outside the repo at

source (import path verified via the `current` junction →

## Round-4 remediation (fifth review)

- **Cancellation (fail-closed):** M1 has no authorized-cancellation
  workflow, so a `CANCELLED` ever-authorized intent never satisfies its
  obligation, regardless of `run.cancellations` contents. Any nonempty
  `run.cancellations` is rejected in verification as unsupported evidence
  (`unsupported_cancellation_evidence`), and each ever-authorized
  `CANCELLED` intent fails `intent_cancellation:<id>` with the obligation
  explicitly unresolved; the engine therefore cannot reach `COMPLETED`.
  Never-authorized `PROPOSED` withdrawal by omission is unchanged and
  needs no fabricated evidence. `run.cancellations` stays in the model
  only as a reserved container for a future workflow.
- **Trust boundary (Task 3):** no public API or application transition
  can replace an `IntentRecord` or write `run.cancellations` — API inputs
  are only goal/approval fields, and internal transitions never reset
  `ever_authorized` (modification only clears `authorized`). Replacing a
  record requires direct in-process memory access, i.e. trusted code in
  the single-process deployment; persistence across restart is M3 scope.
  Even then, an ever-authorized `CANCELLED` state fails verification.

## Round-3 remediation (fourth review)

- **Cancellation:** planning omission never cancels an AUTHORIZED intent.
  Omitted AUTHORIZED -> explicit `intent_conflict`; omitted COMMITTED is
  preserved with its evidence; only never-authorized PROPOSED intents may be
  withdrawn by omission. No cancellation workflow exists in M1 (by design):
  authorized cancellation requires future explicit evidence bound to run,
  intent ID, payload fingerprint, actor/policy authority, decision,
  timestamp and audit event (`run.cancellations` is the evidence container;
  a bare CANCELLED status never satisfies verification).
- **Evidence:** verification resolves intents from canonical run-owned
  records; PROPOSED/CANCELLED intents with ledger transactions are integrity
  conflicts, foreign tx references are rejected, and `sync_intents` may only
  move AUTHORIZED -> COMMITTED (CANCELLED/CONFLICT can never resurrect;
  late commits surface as verification integrity conflicts).
- **Redaction:** standalone secret-marker values are redacted anywhere in
  text, in addition to key=value and whitespace-delimited credential forms.

## Round-2 remediation (third review, superseding position-based manifest)

- **Stable intent identity:** `IntentRecord` (`run.intents`) carries a
  backend UUID independent of revision order/step index. Matching ID-less
  revisions: exact payload match only when unambiguous (identical payloads
  match distinct intents by count); changed committed intent -> explicit
  `intent_conflict` failure (never silent rewrite, never second payment);
  single changed uncommitted intent -> modification requiring
  re-authorization with its proposed payload retained; ambiguous matching
  fails closed; removed uncommitted intents are explicitly CANCELLED.
  New intents keep their proposed payload and need approval; approval binds
  intent IDs, payloads and the exact execution snapshot. Every mutation is
  idempotent by operation ID (= intent ID) and re-verified at the boundary.
- **Manifest coverage (N4):** before COMPLETED, every required authorized
  intent must show exactly one ledger transaction matching its canonical
  authorized payload (accounts, amount, currency) under its own ID, or be
  explicitly cancelled while uncommitted. Intent identity is retained in
  verification checks and audit evidence across revisions.
- **Redaction (N5):** whitespace-delimited credential forms
  (`Authorization <v>`, `secret <v>`, `credentials are <v>`) are redacted in
  semantic issues, persisted errors and API responses, with digit/length
  guards against false positives in ordinary prose.
- **FX (N6):** unsupported pairs raise `ToolValidationError`; 1.0 exists
  only as the explicitly supported USD->USD identity rate.
- **Budget:** the original low-budget scenario again fails before any
  payment/call, with the corrected input+output reservation accounting.

## Remediation corrections (second review, superseding stabilization claims)

- **Payment-intent manifest:** `run.operations` is an authoritative ordered
  manifest, separate from payload matching. A revision's Nth mutating intent
  inherits the Nth manifest intent's identity and originally authorized
  payload — a 100→101 re-plan produces `[100]`, never `[100, 101]` (same for
  changed accounts/currency; reordered/removed steps covered by tests).
  Intents beyond the manifest are unauthorized new business operations and
  require explicit approval (`AWAITING_APPROVAL`) before execution; the
  executor re-checks authorization + payload fingerprint at the mutation
  boundary.
- **Exact snapshot binding:** approval stores the snapshot and its digest
  (`approved_hash`); only that snapshot may execute and digest mismatch is
  rejected before any ledger mutation (approved-1500/modified-1700 probe).
  `is_approved` accepts the snapshot only — no either/or fallback.
- **Authoritative verification:** the expected operation ID comes from the
  approved execution snapshot, never from tool results; result-supplied IDs
  and tx references must agree with ledger evidence read under that ID.
- **Semantic attempts:** every attempt counts, including provider exceptions
  and malformed responses, checked/incremented atomically before the call.
  The initial call is attempt 1; `TRUSTFLOW_SEMANTIC_MAX_ATTEMPTS` (default 3)
  bounds the total. Concurrent retries/reconciles are claimed atomically and
  other callers receive the current state, not a transition exception.
- **Schemas:** provider `REVIEW_SCHEMA` and local `SemanticReviewInput` agree
  (all fields required, confidence 0–1, string issues). The plan schema now
  covers every tool argument property including `list_transactions.limit`.
- **Usage:** missing-steps and later validation failures preserve incurred
  usage (records carry it through errors); attempts are numbered per purpose;
  reservations include estimated input plus allowed output; records are kept
  even when over budget.
- **Sanitization/cleanup:** semantic issues are sanitized at creation and all
  persisted/API-visible errors stay sanitized in pending and terminal states;
  successful recovery clears the active `error` while the audit trail keeps
  the historical failures.

## Stabilization corrections (post-review, superseding earlier M1 claims)

- **Operation identity:** backend-minted UUID per authorized payment intent,
  retained across retries/revisions by (canonical payload fingerprint,
  occurrence ordinal). Two same-route transfers of 10 and 20 — and two
  identical intents — are distinct operations. Reusing an identity with a
  conflicting payload raises `ConflictingOperationError` in the ledger.
- **Revision reconciliation:** a revised plan that references a committed
  operation gets that ledger evidence reconciled into the *current* step's
  result (identity + payload equivalence required). Read steps always
  re-execute fresh; they are never skipped from a previous revision.
- **Late commits:** a step timeout yields `UNCERTAIN` / run status
  `EXECUTION_UNCERTAIN`. Workers are tracked (cancelling an await does not
  stop a thread), conflicting replacements are blocked, and
  `POST /workflows/{id}/reconcile` resolves outcomes from workers/ledger.
- **Verification recovery:** semantic output is validated against an explicit
  Pydantic contract. The deterministic report and committed evidence persist
  before semantic review. Provider/timeout/validation failures and semantic
  FAIL land in `VERIFICATION_PENDING`; `POST /workflows/{id}/verify-retry`
  retries review only — no tool execution, no new transfers, no re-planning.
  A semantic failure never rolls back a committed transfer.
- **Usage:** per-workflow trackers attributed at call time (no shared
  queues). Pre-call conservative reservation against the output cap; usage is
  extracted before response validation and preserved on failures; unknown
  tokens are recorded as unknown (`null`), not zero; over-budget calls stay
  in `llm_calls` flagged `over_budget`. Enforcement is an application-side
  estimate, not a guaranteed provider billing cap.
- **Contracts:** `TRUSTFLOW_LLM_MODE` accepts only `fake|live` (any case) at
  startup; anything else is a startup error, never silent Fake. The plan
  schema covers every tool field including `fx_quote.from_currency/to_currency`.
- **Safeguards:** persisted errors, API errors and audit payloads are
  recursively sanitized (nested dicts/lists, `key=value` secrets). Approved
  execution runs from an isolated deep snapshot. Deterministic verification
  independently reads ledger transactions and matches the complete approved
  operation (accounts, amount, currency, operation identity, tx id).

## Safety invariants added in M1

- Plans are validated (tool allowlist, Pydantic arg schemas, deterministic
  preconditions: known synthetic accounts, no self-transfer). At most **one**
  schema-repair attempt, then the workflow fails closed.
- Approvals are atomic in-process (lock around validate+record+transition),
  bound to plan version + SHA-256 hash over normalized executable args and
  stable `operation_id`s; replays are rejected.
- A committed transfer can never repeat: mutating steps carry a stable
  `operation_id` (run + parties + currency, independent of plan version and
  step id); the ledger is idempotent per key, the executor skips committed
  operations, timeouts reconcile against the ledger, and the verifier checks
  the executed amount against the approved plan amount.
- Semantic review (Wonder) receives the goal, the approved plan, and ledger
  evidence read independently from the ledger. It can only add failures;
  deterministic policy/verification remain authoritative.

## Budgets, retries, cost

Raw `httpx` (no SDK), so there is exactly one retry layer:
`1 + TRUSTFLOW_LLM_MAX_RETRIES` attempts, backoff on 429/5xx/transport errors,
per-call timeout `TRUSTFLOW_LLM_TIMEOUT_SECONDS`, output cap
`TRUSTFLOW_MAX_OUTPUT_TOKENS`, per-workflow token budget
`TRUSTFLOW_TOKEN_BUDGET_PER_WORKFLOW` (exceeding fails closed). Every call is
recorded on the run (`llm_calls`: model, request ID, latency, tokens, estimated
USD cost at official standard rates: Wonder $4/$20, Spark $1.25/$4.25 per 1M).
`expense_category` is always `application_inference`; Muse coding-agent
expenses are a separate subscription and are never counted here.
