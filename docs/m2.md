# TrustFlow M2 — Policy Retrieval and Evidence Spans

## Scope and source of requirements

M2 is the synthetic in-repository scope agreed after M1 acceptance.
It is **not** a reproduction of any external Playbook: no Playbook was
provided. The agreed M2 scope is:

- policy-retrieval and evidence-span scenarios for both source types:
  versioned synthetic policies and deterministic ledger-evidence
  snapshots;
- at least 8 new eval scenarios, at least 30 eval scenarios in total
  (22 pre-existing M1 scenarios are preserved unchanged in behaviour);
- retrieval is advisory. Deterministic `PolicyEngine` checks and
  deterministic ledger verification remain the only authorities for
  risk, approval, tool permission and completion.

Out of M2 scope (unchanged assignments): persistence / restart /
multiprocess (M3), AuthN/RBAC, authorized-cancellation workflow,
dashboard/streaming, real money, deploy. P2 (live harness reservation)
and P3 (live harness request counters) must be fixed and verified
offline before any future paid run; they do not block offline M2 work
and no paid calls are part of M2.

## Text span contract

An evidence span cites an exact fragment of an exact source text.

- `start` is inclusive, `end` is exclusive: the cited text is exactly
  `source_text[start:end]`, with `0 <= start < end <= len(source_text)`.
  No normalization, trimming or whitespace folding is applied.
- Offsets are counted in Unicode code points (Python `str` indices)
  over the decoded source text.
- `text_hash` is the lowercase hex SHA-256 of the cited text encoded
  as UTF-8: `sha256(quoted_text.encode("utf-8")).hexdigest()`.
- Offsets are strict JSON integers: booleans, strings and fractions
  are rejected; an integer-valued JSON number (`0.0`) stays valid,
  matching the M1 numeric contract.
- A policy span must belong to its declared chunk: `chunk_id` is
  resolved through the authoritative corpus (document and corpus
  version included) and the span range must lie inside that chunk.
  A correct `text_hash` alone never validates an unknown or foreign
  chunk (`policy-fx#999` is rejected).
- A span records `source_type` (`policy` or `ledger`), `source_id`,
  `chunk_id`, `start`, `end`, `quoted_text` and `text_hash`. Policy
  spans also record `corpus_version` and the document `version`;
  ledger spans also record `snapshot_id` and `snapshot_hash`.

## Policy corpus contract

- The synthetic policy corpus lives in the repository, has a single
  `corpus_version`, and every document has `doc_id`, `version`,
  `title` and full `text`. Documents are chunked deterministically by
  paragraphs; a chunk records its exact offsets in the document text.
- Retrieval is deterministic lexical retrieval (token overlap) with
  `Settings.retrieval_top_k` and `Settings.retrieval_min_score`. No
  external service, embeddings or paid calls are used.
- Retrieved text is untrusted data. It is passed to a model only as
  delimited context, never as instructions. It cannot change risk,
  approval requirements, limits, the tool allowlist or any
  deterministic check. Prompt-injection text inside a retrieved
  document has no authority.

## Ledger evidence snapshot contract

- A ledger snapshot is an immutable, deterministic serialization of
  balances and transactions read directly from the synthetic ledger
  at snapshot time: canonical JSON with sorted keys, separators
  `(",", ":")`, encoded as UTF-8 for hashing.
- `snapshot_hash` is the lowercase hex SHA-256 of that canonical
  text; `snapshot_id` is `ledger-` plus the first 16 hex characters
  of the hash. The snapshot stores its own canonical text, so a span
  citing it stays valid and unchanged when later transactions commit;
  later state produces a different snapshot with a different id/hash.

## Citation obligation, integrity, relevance, authority

These properties are checked separately; none implies another.

- **Integrity**: offsets in bounds, `quoted_text` equals the exact
  source slice, `text_hash` matches, source id, corpus/document
  version or snapshot id/hash match the cited source.
- **Relevance**: a deterministic lexical overlap between the cited
  text and the claim/query it is cited for, at or above the
  configured minimum. An intact span can still be irrelevant.
- **Authority/truth**: only `PolicyEngine` and the deterministic
  ledger verifier decide risk, approval and whether an operation
  happened. A valid, relevant citation never authorizes a transfer,
  lifts a limit, permits a tool or overrides a deterministic FAIL.

Ledger citations are bound to operations, not ordering: each ledger
span cites the transaction found in the ledger by the plan step's
backend-owned operation/intent key, with payload equality checked
against the snapshot. A snapshot must provably contain this
workflow's operations — a self-consistent snapshot of another ledger
is rejected even when its own hash matches. Ledger relevance means
citing one of this plan's own transactions; an arbitrary intact slice
of a snapshot is `span_irrelevant`, and a missing citation for a
committed operation is `span_coverage_missing`. Server-selected
citations are evidence about retrieved sources and ledger state, not
grounding of any particular model `summary`/`issues` claim: no
claim-to-citation link is created or claimed.

Snapshot lifecycle: the snapshot stored on the run is reused while
it still covers the plan's operations, so another workflow's later
commits cannot break a healthy verification retry. If coverage no
longer holds, snapshot and ledger spans are replaced atomically as a
pair and the rotation is audited (`ledger_snapshot_rotated`); old
spans are never validated against a new snapshot.

Reservation: the planner reserves for the bounded retrieval context
actually transmitted (identical bounded text in the estimate and in
the initial, repair and transport-retry calls). Advisory semantic
context that does not fit the remaining budget is dropped from the
transmitted payload and the reservation is recomputed for what is
actually sent; incurred usage is never dropped. Mandatory evidence
is never dropped for budget — its reservation failure propagates.
Retrieval context is passed to a provider only when the actual
`propose_plan` callable accepts the keyword (signature-checked);
legacy overrides without it keep M1 behaviour and are never retried
after a `TypeError`.

Citation obligation has two modes:

- **Advisory (default, all pre-existing M1 workflows):** retrieval
  may be attached to a run and audited. Missing or invalid advisory
  citations do not block planning, execution or completion and never
  change an outcome.
- **Mandatory (explicit opt-in only, `WorkflowGoal.require_evidence`):**
  mandatory evidence is part of that workflow's contract.
  - If mandatory pre-execution evidence is unavailable or invalid,
    the workflow fails before any mutation: no transfer is executed.
  - If a span error is discovered after a commit, the transfer, the
    deterministic report, usage records and audit are preserved. The
    run enters bounded verification-only recovery
    (`VERIFICATION_PENDING`, then `FAILED` at
    `Settings.semantic_max_attempts`), exactly like a semantic-review
    failure. Recovery never re-executes tools, never creates a second
    transfer and never re-plans with re-execution to fix citations.

## Error codes

Span/retrieval validation reports stable codes: `span_out_of_bounds`,
`span_text_mismatch`, `span_hash_mismatch`, `span_version_mismatch`,
`span_source_mismatch`, `span_chunk_mismatch`,
`span_coverage_missing`, `span_malformed`, `span_irrelevant`,
`retrieval_unavailable`. Advisory-mode findings are audited with
these codes; mandatory-mode findings follow the fail-closed rules
above. Mandatory-mode preparation failures raise the typed
`EvidenceValidationError` / `LLMResponseError` into bounded
verification-only recovery; there is no fail-open path that turns a
preparation error into absent evidence.
