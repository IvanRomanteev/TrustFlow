## M3 implementation (minimal vertical slice)

### Persistence (`src/trustflow/persistence/`, stdlib `sqlite3` only)

- Enabled by `TRUSTFLOW_DB_PATH` (`Settings.db_path`). Unset keeps the
  exact M1/M2 in-memory behaviour, so all pre-existing tests run
  unmodified. Docker Compose and the demo always set it.
- `SQLiteRunRepository`: same `save/get/list` API. Full `WorkflowRun`
  JSON plus `status`/`version` columns. Optimistic concurrency: the
  version loaded by `get()` must still match on `save()`, otherwise
  `ConcurrentUpdateError` (API 409). This makes hash-bound approval
  single-use across processes, not only under an in-process lock.
- `PersistentLedger`: same ledger API as `SyntheticLedger` (subclass;
  balances/transactions always read from SQLite). One
  `BEGIN IMMEDIATE` transaction per transfer: idempotency lookup,
  balance checks/updates and transaction insert commit atomically.
  `UNIQUE(idempotency_key)` is the cross-process backstop: a racing
  duplicate returns the committed tx for an identical payload and
  raises `ConflictingOperationError` for a different payload — exactly
  the in-memory contract. WAL journal + `busy_timeout` for concurrent
  readers/writers. `fail_next_transfer` stays a per-process test hook.
- `SQLiteAuditLogger`: same `log/list` API, append-only table (no
  update/delete path), payload hashing/redaction unchanged.
- Approvals, step results, verification reports, evidence spans,
  snapshots and `llm_calls` are durable because they live inside the
  persisted `WorkflowRun`. Approval rows are additionally constrained
  by the optimistic run version (see above).
- Migrations: `schema_migrations` table; v1 creates all tables.
  Opening an existing database is a no-op (idempotent).
- Atomicity boundary (honest): each store commits atomically; the
  ledger commit and the run save are two commits. A crash between
  them is safe, not hidden: the executor checks the ledger by
  operation key before any transfer, and restart recovery (below)
  never re-executes. No distributed transaction is claimed.

### Restart recovery

On container start in persistent mode, non-terminal runs left in
`EXECUTING`/`VERIFYING` by a crash move `-> VERIFYING ->
VERIFICATION_PENDING` with error `Recovered after restart;
verification-only recovery, no re-execution` and a
`restart_recovered` audit event. `AWAITING_APPROVAL`,
`VERIFICATION_PENDING` and `EXECUTION_UNCERTAIN` are left untouched
(approval binding and reconcile semantics survive restart).
Recovery never executes tools or transfers; `verify-retry` stays
verification-only, so a committed payment can never repeat and an
uncommitted interrupted execution fails closed.

### API

- `GET /workflows` lists runs (newest first) for the demo UI.
- Approval authorization: when `TRUSTFLOW_APPROVAL_TOKEN`
  (`Settings.approval_token`) is configured, `approve`, `reject`,
  `verify-retry` and `reconcile` require header
  `X-Approval-Token` (constant-time compare); missing -> 401, wrong
  -> 403. Unset keeps M1/M2 local-test behaviour; the demo Compose
  file always sets a token and the UI cannot approve without it.
  The token is never logged or persisted (redacted by key name).
- CORS for the local demo origins (`Settings.cors_origins`).

### Demo UI (`frontend/`, Next.js + React + TypeScript)

Three panels on one page: (1) task input creating a synthetic
workflow, (2) run timeline (status, plan steps, step results,
verification checks, evidence spans/snapshot, audit events,
`llm_calls`), (3) approval & evidence (exact `plan_hash`, operation
details from plan steps + intents, approve/reject). A permanent
`SANDBOX / NO REAL FUNDS` banner is always visible. State polls the
FastAPI backend every 2 s; the backend is the only source of truth;
the selected run id survives a browser refresh (`localStorage`).
Pending verification, uncertain execution, blocked/failed and
rejected states are shown as-is with `verify-retry`/`reconcile`
actions; the UI never renders a transfer as successful unless the
backend run/evidence says so. The approval token is entered in the
UI and kept in `sessionStorage` only.

### Reproducible demo

- `docker compose up --build`: backend on `:8000`, UI on `:3000`,
  SQLite on a named volume, fake LLM mode, approval token set.
- Deterministic fake-mode scenarios (API-level, `tests/api/test_m3_demo.py`):
  ordinary success, HIGH-risk approval, semantic failure ->
  verification-only recovery, evidence/policy failure blocking
  completion (`require_evidence` with unretrievable mandatory
  evidence fails before any mutation). Fake responses are labelled
  fake everywhere; no Meta call is implied.

## Remediation round 1 (independent review of 695bfd8: F1–F7)

All seven findings are fixed by the developer and await independent
re-review; M3 is not accepted. Maintained regressions:
`tests/unit/test_m3_remediation.py` (real `os._exit` child processes,
concurrent ASGI decisions, budget/attempt restart controls).

- **F1 (P1):** durable checkpoints before side effects — plan +
  intent/operation IDs at `PLANNED`, approval claim (decision +
  exact snapshot + `EXECUTING`) CAS-saved before execution, and an
  `EXECUTING` save before the executor runs (initial and revision).
  Startup recovery reconciles committed transfers from the ledger
  by authoritative operation key (payload + authorization checked),
  refreshes reads, and moves stranded execution to
  verification-only recovery; pre-checkpoint interruptions fail
  closed. A paid run can no longer be rejected after restart.
- **F2 (P1):** per-record CAS. Each loaded `WorkflowRun` carries
  `persistence_version` (excluded from API/storage JSON); SQLite
  `save()` compare-and-sets that exact version. Approve/reject
  persist the winning decision before execution/audit; losers get
  409 with no successful-decision audit event.
- **F3 (P2):** `UsageTracker` rehydrates from persisted
  `run.llm_calls` (flat records appended as-is, never re-recorded):
  budget, failed-call history and logical/transport attempt
  numbering survive restart and repeated resumes.
- **F4 (P2):** the semantic attempt increment is saved before the
  reviewer is invoked; a crash after a completed review consumes
  the attempt permanently and the bound still terminates `FAILED`.
- **F5 (P2):** deterministic FAIL in verification-only recovery is
  terminal `FAILED` with an auditable reason (no infinite pending,
  no re-execution, no fabricated results). An uncertain step with
  no live worker and no ledger commit (post-restart) resolves as
  definitively not committed in reconcile.
- **F6 (P2):** frontend refresh carries a monotonic generation +
  selected-run guard; action responses supersede in-flight polls,
  and stale or wrong-run responses are never applied. Verified in
  headless Chrome with a held `AWAITING_APPROVAL` response delivered
  after a completed approve: UI stays `COMPLETED`, controls disabled.
- **F7 (P2):** the UI derives the deterministic verdict from the
  actual deterministic checks (unknown when none are reported) and
  shows semantic and overall results separately. Verified in Chrome
  against an injected semantic FAIL: deterministic PASS, semantic
  FAIL, overall FAIL, status `VERIFICATION_PENDING`.

## Remediation round 2 (independent re-review of 8143dbc: N1 + N2)

F1–F4, original F6 and F7 were independently VERIFIED FIXED and are
unchanged. The two items below are fixed by the developer and await
independent re-review; M3 is not accepted. Maintained regressions:
`tests/unit/test_m3_remediation2.py`.

- **N1 (P1):** `WorkflowEngine.reconcile` routed a definitively
  resolved dead worker (no live task, no ledger commit) into the
  ordinary revision loop, so recovery itself planned and executed a
  replacement transfer (ledger 0→1, `plan_revised`). Reconcile now
  verifies through the verification-only branch
  (`semantic_only_retry=True`): a dead worker with no commit ends in
  bounded `FAILED` with zero planner calls and zero mutating tool
  calls; a committed operation still reconciles from the ledger and
  completes verification-only; a live tracked worker stays
  `EXECUTION_UNCERTAIN` until it resolves. Normal initial planning
  and revisions are untouched.
- **N2 (P2):** a late action response unconditionally re-selected
  its own run, overriding a newer user selection. `act()` now
  captures the selected run before awaiting; when the current
  selection differs on arrival, the response only refreshes the run
  list and the still-selected run (with a non-disruptive notice),
  never the visible run/evidence/audit or `localStorage`. Verified
  in headless Chrome: delayed approve of A while B is selected —
  selection and panels stay on B, backend A completes normally.

## Known limitations

- Single-instance SQLite demo; no Postgres, no multi-host deployment.
- `Executor._pending` worker tracking is in-process: after a restart
  an `EXECUTION_UNCERTAIN` run is reconciled from the ledger only.
- Approval authorization is a shared demo token, not user AuthN/RBAC
  (still future scope, as in M1/M2).
- Live Meta behaviour is unchanged and was not exercised (no paid calls).
