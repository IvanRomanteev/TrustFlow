## Preserved architecture and safety invariants (all phases)

These M1–M4 contracts are not redesigned in M5:

- Risk is decided by the deterministic backend `PolicyEngine`, never by
  the LLM alone.
- Approvals are bound to an immutable plan version + SHA-256
  `plan_hash`; repeats/replays are rejected (HTTP 409). The approval
  decision + exact snapshot + `EXECUTING` are CAS-persisted before any
  execution.
- Mutating tools are idempotent (operation/idempotency key + ledger
  `UNIQUE` backstop); succeeded steps are never re-executed on
  retry/resume/restart.
- Restart recovery is verification-only (`VERIFICATION_PENDING`,
  `EXECUTION_UNCERTAIN` + reconcile from ledger evidence); recovery
  never executes tools, transfers or model calls.
- Semantic-review attempts and the per-workflow token budget survive
  restart; usage is isolated per workflow and failed calls are recorded.
- Secrets come only from the environment; approval token and API keys
  are never logged or persisted; error output is sanitized.
- The frontend renders backend state only (authoritative GETs); it
  never renders a transfer as successful unless backend evidence says so.

### P1-01 — wildcard publication broke the local-only boundary (fixed)

- Reproduced independently: the default Compose published the backend
  (and frontend) without `host_ip`; Docker showed `0.0.0.0`/`::`
  bindings. A client outside the Compose network reached the host
  Ethernet IPv4 (`192.168.0.11`) and, using the public demo token,
  approved a HIGH-risk synthetic transfer; the transfer was confirmed
  by direct SQLite inspection. Pre-existing M3-era defect, not an
  M5.1 code regression. CORS does not restrict non-browser clients.
- Root cause: `docker-compose.yml` published `"8000:8000"` and
  `"3000:3000"` (wildcard) while the only approval credential is a
  public demo constant.
- Fix (smallest change, `docker-compose.yml` only): publish
  `127.0.0.1:8000:8000` (backend) and `127.0.0.1:3000:3000`
  (frontend). No approval/API/engine/persistence/CORS/frontend change.
- Security boundary after the fix: trusted **local-only** demo. The
  loopback binding removes Ethernet/LAN reachability of the published
  ports. It does **not** protect against untrusted local processes or
  Docker daemon access; Docker Desktop may still expose
  `host.docker.internal` to containers. No production authentication
  is added or claimed, and no cloud/public readiness is implied.
- Developer verification (isolated Compose project with dynamically
  allocated free loopback ports in an override that preserves
  `host_ip`, fresh volume; pre-existing containers/volumes untouched):
  `docker compose config --format json` shows `host_ip=127.0.0.1` for
  both services and no wildcard binding; real `docker inspect`
  bindings confirm `127.0.0.1`; loopback health/frontend/flow pass;
  backend restart keeps a single transfer and replay returns 409;
  HTTP to the host Ethernet IPv4 on the published ports fails to
  connect. Maintained gate:
  `tests/integration/test_m5_docker_e2e.py` (opt-in, see below).
- Operator note: already-running containers keep their old bindings
  until recreated (`docker compose up -d`); the fix is in the
  committed configuration, not retroactively in live containers.

### P2-05 Remediation R2 (this commit; awaiting independent re-review)

- **Tri-state inspection contract:** `_inspect_image` returns
  `InspectResult` with state FOUND / NOT_FOUND / ERROR. NOT_FOUND
  requires all real-CLI absence signals together (nonzero exit,
  stdout exactly `[]`, daemon `No such image: <ref>`); FOUND
  requires valid metadata (single object, `sha256:` ID, labels).
  Daemon/permission/transport/timeout/malformed results are ERROR,
  and ERROR aborts tag allocation, sentinel setup and cleanup
  before any mutation. Every consumer (allocation precheck,
  post-build capture, cleanup, sentinel) uses this contract.
- **Immutable-ID cleanup:** the recorded full image ID is the only
  deletion target (`docker rmi <id>`, never a tag, never `--force`).
  Ownership (label + ID) is verified against the image addressed by
  its own ID, so retagging cannot redirect deletion. Docker
  refusals (multiple tags/containers/conflicts) preserve the image
  with a visible `preserved-*`/`cleanup-failed` outcome; nothing is
  silently reported as cleaned.
- **Sentinel redesign:** tests never create or overwrite the legacy
  `trustflow-m5-matcher-test:latest` tag. A pre-existing legacy
  image is inspected read-only and its ID/labels asserted unchanged;
  inconclusive state fails closed. Sentinels use unique
  per-invocation tags and ID-based verified cleanup. (Exercising
  the historical fixed-tag fixture destructively would require an
  exclusively owned isolated daemon and is intentionally not done
  on a shared developer daemon.)
- **RED/GREEN evidence (developer):** against the blocked R1 module
  extracted read-only from `3c0cc9c`, an isolated harness showed
  daemon-error inspect -> `None`, removal argv targeting the
  mutable tag, and — on real Docker — old cleanup deleting
  replacement image B while A survived. On this candidate the same
  scenarios are GREEN via the maintained suite: 12 fake-runner
  adversarial unit tests (absence/found/daemon/permission/malformed/
  timeout/allocation/sentinel-guard/cleanup matrix) plus real-Docker
  tests for inspect states, retag race (B preserved), multi-tag
  refusal, sequential distinct tags, concurrent isolation, sentinel
  preservation, matcher and stack loopback behaviour (9/9 opt-in,

### P2-05 Remediation R3 (this commit; awaiting independent review)

- **Strict absence contract:** NOT_FOUND now requires nonzero exit,
  stdout exactly `[]`, and stderr reduced to exactly one complete
  line equal to `Error response from daemon: No such image: <ref>`
  for the exact requested ref (anchored full-message equality;
  quoted/embedded/mixed/extra-line/prefix/suffix variants are
  ERROR). Validated against the real local Docker CLI (genuine
  missing -> NOT_FOUND, existing -> FOUND in the opt-in suite).
- **Metadata validation:** FOUND requires a one-element list with a
  dict item, `Id` matching `sha256:<64 hex>`, dict `Config`, and
  `Labels` absent or a dict of string->string; anything else is
  ERROR (no exceptions leak as crashes).
- **Safe teardown policy:** the integration module now contains
  exactly one `docker rmi` call — the ID-addressed, label-verified
  cleanup helper. Fixtures retire extra tags only by *building a
  scratch image over the tag* (a tag write, which cannot delete any
  image) and then deleting strictly by recorded IDs. A dedicated
  real-Docker regression retags `extra_tag` to image B at the
  teardown boundary: B stays intact, A is removed only by ID.
  Residual limitation: if Docker refuses an ID deletion (multiple
  references/containers), the fixture preserves the image with a
  visible diagnostic instead of forcing anything.
- **Diagnostics (P3-B/C):** fixture builders raise with the unique
  tag, inspect state/detail and "ownership unknown, cleanup
  intentionally not attempted"; all fixture teardowns aggregate
  cleanup outcomes (primary failures preserved, cleanup failures
  asserted or warned visibly, leftovers identified by tag/ID).
- **RED/GREEN (developer):** against R2 extracted read-only, the
  quoted/mixed/wrong-suffix patterns returned false NOT_FOUND and
  the unchanged old multi-tag test deleted retagged B while
